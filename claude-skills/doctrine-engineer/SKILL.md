# Skill — Organizational Doctrine Engineer

## Purpose

Determine whether a repeated lesson deserves to change future organizational behavior.

## Promotion pipeline

```text
experience
→ lesson candidate
→ evidence review
→ replay
→ simulation
→ shadow
→ governance approval
→ active doctrine
```

## Doctrine package

Must contain:

- ID/version,
- scope,
- triggering conditions,
- rule/procedure,
- rationale,
- evidence,
- tests,
- performance history,
- conflicts,
- rollback,
- owner/approval.

## Rejection criteria

Do not promote if:
- success depends on one repository-specific accident;
- evidence is correlated;
- rule creates unacceptable rigidity;
- the existing compiler/policy can solve the problem more simply;
- no replay test can distinguish improvement.

## Change control

Doctrine should be slower-moving than mission strategy. Preserve previous versions and support rollback.
